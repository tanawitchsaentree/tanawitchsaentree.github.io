# แผนแก้ showcase — ฉบับปรับทิศทาง

วันที่ 26 กันยายน 2026

## 1. โจทย์ที่ยึดในรอบนี้

เดโมใน portfolio มีหน้าที่ให้คนดูเข้าใจงานออกแบบผ่านภาพและลำดับการสาธิต ผู้ชมไม่ควรต้องกรอกข้อมูล เล่นแอป หรือค้นหาปุ่มที่ถูกต้องเพื่อเห็นประเด็นสำคัญ

คำชี้แจงล่าสุดของเจ้าของงานมีผลเหนือแผน `demo-audit-sol-handoff.md` โดยเฉพาะข้อเสนอให้ต่อ flow ให้เล่นได้ทั้งหมด ปุ่มที่เป็นส่วนหนึ่งของภาพจำลองแต่ไม่ได้กดใช้งาน ไม่ถือเป็นบั๊กโดยตัวมันเอง

เป้าหมาย: เปิดมาเห็นหน้าที่สมบูรณ์ ดูต่อแล้วเห็นการเปลี่ยนแปลงที่มีเหตุผล อ่านทัน และเข้าใจว่าผู้ออกแบบตัดสินใจแก้อะไร โดยไม่ต้องคลิก

สิ่งที่ยังสำคัญแม้เป็น showcase: ข้อมูลตัวอย่างต้องไม่ขัดกัน ผลลัพธ์ต้องตรงกับเหตุการณ์ สถานะต้องไม่ตกค้าง ภาพต้องไม่ถูกตัดผิดตำแหน่ง และจังหวะวนซ้ำต้องไม่ดูเป็นอาการกระตุกหรือบั๊ก

## 4. รูปแบบ showcase ร่วม

### 4.1 ลำดับฉาก

แต่ละฉากต้องกำหนด 4 อย่างก่อนเขียนโค้ด: สถานะตั้งต้น → การเปลี่ยนแปลงหนึ่งอย่าง → ผลที่ต้องการให้เห็น → จุดจบที่อ่านได้

- เริ่มเมื่อส่วนสำคัญของเดโมอยู่ใน viewport และแท็บ browser ยังเปิดให้เห็น
- หน้าแรกของเดโมต้องสวยและสื่อความหมายตั้งแต่ยังไม่เริ่ม animation
- ตั้งต้นค้างประมาณ 2–3 วินาที; transition 300–600 ms; ผลลัพธ์ค้างอย่างน้อย 4–6 วินาที ปรับตามปริมาณข้อมูล ไม่ใช้ตัวเลขนี้เป็นกฎตายตัว
- เดโมที่มีหลายข้อความ/ตารางให้ 12–20 วินาทีต่อเรื่อง แทนการวนเร็วเพื่อโชว์ว่าขยับได้
- ค่าเริ่มต้นเป็นเล่นหนึ่งรอบแล้วค้างที่ผลลัพธ์ที่อ่านรู้เรื่อง มี Replay สำหรับผู้ที่อยากดูซ้ำ
- มี Pause/Resume ที่อยู่นอกภาพแอปและมองเห็นได้ ไม่จำเป็นต้องทำ navigation ภายในแอปให้ใช้งานจริง
- ลดการเคลื่อนไหว: แสดง key state ที่สื่อสารได้พร้อมคำบรรยาย ไม่แค่ซ่อนนิ้วแต่ยังเปลี่ยนข้อมูลเอง
- ออกจาก viewport ให้หยุดเวลา; กลับมาให้ต่อจากจุดเดิม; unmount ให้ยกเลิก timeout/animation ทั้งหมด

### 4.2 สิ่งที่ผู้ชมควบคุม

เหลือเฉพาะการดูผลงาน เช่น Pause, Replay, เลือกฉาก, เปรียบเทียบก่อน/หลัง หรือดูภาพใหญ่ เป็นทางเลือกเสริม ผู้ชมที่ไม่แตะอะไรต้องเห็นใจความครบ

ไม่เพิ่ม cursor/hover/focus ให้ส่วนที่เป็นภาพเฉย ๆ ถ้ารักษา HTML button ไว้เพื่อใช้จัดรูป ให้แยกโหมด presentation และ semantics อย่างเหมาะสม ไม่ทำให้คีย์บอร์ดต้องไล่ผ่านปุ่มจำลองหลายสิบปุ่ม ใช้ figure + caption อธิบายฉาก และให้ screen reader เข้าถึง controls ของ showcase จริง ไม่ประกาศทุก animation frame

### 4.3 ภาพและ spacing

- รักษา hero และลำดับ section ที่เพิ่งปรับ ไม่ออกแบบหน้าใหม่ทั้งหน้า
- ฟอนต์ของคำบรรยายพอร์ตใช้ระบบปัจจุบัน ส่วนข้อความในแอปต้องตรวจขนาดหลัง scale จริง ไม่ดูเฉพาะค่า font-size ต้นฉบับ
- ตรวจ frame, screen inset, มุมโค้ง และ safe area ให้สอดคล้องกัน ไม่มีข้อความลอด notch หรือชิดมุมจนถูก crop
- ลดเงาหรือกรอบที่แย่งสายตาจากจุดสาธิตเมื่อเห็นปัญหาในภาพจริง ไม่เปลี่ยนรูปทรง device ทุกอันโดยไม่มีเหตุผล
- บนหน้าจอแคบต้องไม่ย่อทั้ง dashboard จนอ่านไม่ออก เลือก key frame/พื้นที่สำคัญและมีดูภาพใหญ่ แทนการบังคับให้เลื่อนสองแกนเพื่อเข้าใจเรื่อง
- สีผลิตภัณฑ์ในหน้าจอรักษาเอกลักษณ์เดิมได้ ให้คำบรรยายและพื้นหลังรอบนอกต่อเนื่องกับหน้า project

## 5. แผนรายโปรเจกต์

### 5.1 Allianz — แสดงเหตุผลและผลของการตัดสินใจ

ไฟล์หลัก: `src/demos/allianz/ConfidenceGate.tsx`, `Handoff.tsx`, `PromptEditor.tsx`, `BatchDispatch.tsx`

เรื่องที่ต้องเห็น:

1. Classification: รายการเอกสาร → เน้นหนึ่งรายการที่ไม่มั่นใจ → เปิดเหตุผลกับทางเลือก → แสดง route ที่เลือกและจำนวนค้างที่ลดลง
2. Rule preview: กฎเดิม → เปลี่ยนเป็นอีกกฎหนึ่ง → เน้นเฉพาะแถวที่เปลี่ยน → แสดงกฎที่ใช้แล้ว
3. Fallback: batch เข้า → แยก standard/review → ค้างที่เหตุผลของงานที่ส่งให้คน

ให้ทั้งสามส่วนเริ่มตาม viewport ของตัวเอง ไม่เล่นพร้อมกันทั้งหน้า ไม่ต้องให้ผู้ชมกด Process หรือเปิดแถวเองจึงเห็นผลสำคัญ ใช้นิ้ว/cursor เฉพาะตอนที่ตำแหน่งกดช่วยอธิบายจริง

เก็บการแก้ count และ route จากรอบก่อน แต่จัด state ไว้ที่เจ้าของฉากเดียวกัน ปิด/เปิดรายละเอียดแล้วผลต้องไม่หาย Undo ไม่จำเป็นต้องเป็นฟีเจอร์หลัก และห้ามผูกหน้าต่างเวลา Undo กับ reduced motion ให้คนอ่านไม่ทัน

ตรวจรับ: นั่งดูเฉย ๆ เห็นว่าทำไมต้องส่งให้คนและส่งไปไหน; หลังตัดสินใจไม่มีคำว่า decide ค้างบนรายการสำเร็จ; count ตรงกัน; reset ฉากทำให้ข้อมูลกลับพร้อมกันทุกจุด

### 5.2 Invitrace — ทำให้เห็นว่าอะไรเปลี่ยนร่วมกัน

ไฟล์หลัก: `public/demos/invitrace-ds.html`, `public/demos/project-type.css`

สามเรื่องที่จัดจังหวะแยกกัน:

- Hospital themes: District → Teaching → Specialty ใช้ข้อมูลผู้ป่วยตัวอย่างชุดเดิม เพื่อให้ความแตกต่างของสี density และ radius อ่านได้โดยไม่สับสนว่าคนไข้เปลี่ยนด้วย
- Shared library: ทุก instance linked → มีหนึ่ง detached → เปลี่ยน master → ค้างให้เห็นตัวที่ตามและตัวที่ไม่ตาม
- Theme authoring: เน้น token เพียงหนึ่งบรรทัด → เน้นผลในจอ → ค้าง ไม่เปลี่ยนสี spacing และ layout พร้อมกัน

ตรวจ caption ให้พูดตรงกับสิ่งที่เปลี่ยนจริง เช่น density ต้องเปลี่ยน spacing จริง ไม่ใช่มีแต่ป้ายชื่อ ตรวจ empty state ให้ยอด/รายการ/ข้อความอยู่ในบริบทเดียวกัน และ long name ต้องไม่ทะลุ frame

เก็บ semantic controls และชื่อ swatch ที่แก้แล้ว แต่ autoplay ต้องเป็นลำดับฉากที่รู้จุดจบ ผู้ชมเลือกฉากเองได้และ playback ต้องไม่แย่ง state คืน แก้ให้มี Replay หลังจบ ไม่ใช้การ hover เป็นเงื่อนไขหลักของการหยุด

ตรวจรับ: ไม่กดก็เห็นความต่างอย่างน้อยสอง theme และหลักการ linked/detached; มีเวลาอ่านข้อความ; iframe กับหน้า standalone แสดงเหมือนกัน; สี/ค่า token/active label ไม่ขัดกัน

### 5.3 Profita — เล่าลำดับการซื้อให้ดูจบได้เอง

ไฟล์หลัก: `ProfitaClient.tsx`, `ProfitaPhoneScreen.tsx`, `screens/*`, `ProfitaCase.module.css`

รักษากลุ่มภาพ overview และ supporting screens เป็น gallery ภาพตัวอย่าง งานหลักอยู่ที่ walkthrough กลางหน้า:

Fund list → Fund detail → Amount → Review → Order received โดยใช้กองทุน LHIP-D, ยอด 5,000 และบัญชีตัวอย่างเดียวตลอดเรื่อง

- ใช้ highlight อ่อน ๆ บอกแถวที่เลือก/ยอดที่กรอก แทนการทำ keypad animation ยาว
- ให้ amount กับ review อยู่บนจอนานพอเห็นข้อมูลสำคัญ
- ป้ายขั้นตอนด้านนอกเปลี่ยนตามภาพ จบที่รับรายการพร้อม pending processing ไม่กล่าวว่าเงินลงทุนสำเร็จแล้ว
- ผู้ชมเลือกฉากเองได้ แต่ไม่จำเป็นต่อการเข้าใจเรื่อง
- Supporting screens ค้างภาพที่สมบูรณ์ ไม่ต้องสร้าง flow switch fund, bank history หรือ share receipt เพิ่ม

เก็บ fixture ตัวเลขที่แก้ให้ตรง และการส่งข้อมูลที่ช่วยให้ฉากตรงกัน ใช้เป็นข้อมูลขับ showcase เอาความซับซ้อนที่มีไว้ให้เล่น app เช่นเลือกหลายบัญชี/validation ทุกทาง ออกจากเส้นทางหลักตามความจำเป็น ไม่ลบ validation ที่มีประโยชน์โดยพลการ แต่ไม่ถือว่าเป็น deliverable หลัก

ทบทวนการเปลี่ยนปุ่มเป็นข้อความในรอบก่อน: อย่าเสียรูปลักษณ์หน้าจอผลิตภัณฑ์เพียงเพื่อให้ไม่มีปุ่มกดไม่ได้ รักษาภาพต้นฉบับและประกาศว่าเป็น screen example ที่ระดับ showcase

จุดตรวจภาพที่ต้องเจาะ: supporting ใช้ scale .65 และบาง breakpoint .55; ต้องดูว่าเลข/label อ่านได้จริงหรือไม่ ตัวหนังสือเล็กในแอปไม่ควรถูกบีบจนเหลือจุด แม้ข้อความพอร์ตภายนอกจะใช้ 14 px

ตรวจรับ: ดูครบโดยไม่กด; กองทุน/ยอด/บัญชี/วันที่ตรงทุกฉาก; ภาพไม่กระโดดขนาดเมื่อเปลี่ยนหน้า; step label ถูกทั้งตอนเลือกบัญชีหรือใบรับรายการถ้ายังเก็บฉากนั้นอยู่

### 5.4 Stellareat — สามจอช่วยเล่าเรื่องเดียวกันโดยไม่แย่งกัน

ไฟล์หลัก: `StellarScreen1.tsx`, `StellarScreen2.tsx`, `StellarScreen3.tsx`, `StellarPhone.tsx`, `CompactStories.tsx`

รักษา placement สามโทรศัพท์ แต่กำหนดฉากและ offset ให้คนดูตามทัน:

1. จอแรก: จากหน้าแนะนำไปยังคำถามเรื่องวัตถุดิบ
2. จอที่สอง: แสดงคำขอตัวอย่างและคำแนะนำหนึ่งรายการ ให้ข้อความอ่านทัน
3. จอที่สาม: เลือกวัตถุดิบชุดที่เตรียมไว้ → ผลสูตรที่ใช้วัตถุดิบนั้น → ค้างรายละเอียด

เมื่อทั้งสามจออยู่ใน viewport เดียวกัน ไม่ให้มีนิ้วพิมพ์/เลื่อน/เปลี่ยนผลพร้อมกันทั้งสามจอ ให้เริ่มแบบเหลื่อมจังหวะและส่วนที่ไม่ใช่จุดสนใจค้างภาพ ไม่อ้างว่า state เชื่อมกันจริงหากยังเป็นตัวอย่างแยก

ยกเลิกทิศทางที่เพิ่งบังคับจอสามเริ่ม paused แล้วต้องให้ผู้ชมเลือกเอง คืนการนำเสนออัตโนมัติที่รู้จุดจบ ไม่จำเป็นต้องทำ search/chat/camera จริง และเอาข้อความบรรยายเชิงเทคนิค “first two replay… picker starts paused…” ออก เปลี่ยนเป็น caption ที่บอกเรื่องในจออย่างสั้น

จุดบกพร่องจริงที่ต้องแก้:

- จำนวนวัตถุดิบ, chip ที่เลือก, รายการ “มีแล้ว” และสูตรผลลัพธ์ต้องตรงกัน
- async loop ต้องหยุดได้จริง ไม่ทำ side effect หลัง Pause/unmount
- เริ่มรอบใหม่ต้องไม่สร้าง chip หรือข้อความซ้ำ
- คำนวณตำแหน่งนิ้วสัมพันธ์กับ screen หลัง scale .85 ไม่ให้ชี้คลาด
- reset ไม่เปิดเผยภาพกะพริบหรือ scroll กระโดดให้เห็น

ตรวจรับ: ดูแล้วเข้าใจ input → suggestion; recipe ตัวอย่างไม่อ้างว่าใช้สิ่งที่ไม่ได้เลือก; Pause หยุดทั้งนิ้ว ข้อความ และการเลื่อน; แก้ reduced motion ให้เห็นผลลัพธ์ที่เข้าใจได้ทันที

### 5.5 Vitae — คืน showcase ที่อธิบาย score ได้

ไฟล์หลัก: `VitaeAppScreen.tsx`, `useFingerBot.ts`, `PhoneShell.tsx`

ฉากหลัก: daily summary → เน้น “vs your 14-day baseline” → เปิด 4 inputs → ค้างข้อมูลที่อยู่เบื้องหลัง score

ไม่ใช้การแตะ “Mark done” แล้ว score กระโดด 82 → 88 เป็นเรื่องหลัก เพราะทำให้ดูเหมือนรับรองความสัมพันธ์ระหว่างเดิน 10 นาทีและคะแนนสุขภาพ ทั้งที่สูตรในตัวอย่างไม่ได้พิสูจน์เรื่องนี้ ถ้าจะคง daily move ให้เปลี่ยนเพียงสถานะกิจกรรม และไม่เปลี่ยน score โดยไม่มีที่มาจาก fixture

เอาการลบ autoplay เพื่อบังคับ click ในรอบก่อนมาปรับใหม่: ใช้ state ที่ควบคุมได้และ sequence อัตโนมัติ แต่ไม่คืน DOM mutation หลายตัวที่แข่งกัน ให้ Replay/Pause ควบคุม sequence เดียว

ไม่เปลี่ยน active tab เป็น Trends ถ้าเนื้อหายังเป็น Today จะรักษา tab bar ในฐานะองค์ประกอบภาพได้โดยไม่ animate มัน ห้ามสร้าง trends feature ใหม่เพื่อรองรับฉากที่ไม่เกี่ยวกับ case

ตรวจรับ: ผู้ชมเห็น inputs โดยไม่กด; score ไม่เพิ่มเองเพราะ effect ตกแต่ง; label ของการเปิด/ปิดตรงภาพ; collapsed content ไม่ถูกอ่านเหมือนเปิด; ค้างผลลัพธ์ไม่รีเซ็ตก่อนอ่านทัน

### 5.6 Tim Hortons — โชว์การแก้ออร์เดอร์จากประสบการณ์หน้างาน

ไฟล์หลัก: `public/demos/tims-pos.html`, `TimsiPadMockup.tsx`

ฉากตัวอย่างเดียวที่เล่าครบ: medium double-double → เพิ่มใน ticket → เปลี่ยนเป็น oat/size อย่างใดอย่างหนึ่ง → Update → ticket และราคาเปลี่ยน → จบที่ออร์เดอร์พร้อมส่ง

เน้นการอยู่ร่วมกันของ controls และ ticket การแก้ล่าสุดต้องมองออกว่าเปลี่ยนแถวไหน ไม่จำเป็นต้องจบด้วยระบบชำระเงินหรือใบเสร็จเพื่อพิสูจน์งานออกแบบ POS

เก็บการป้องกัน pending edits และแก้ remove/undo จากรอบก่อน เพราะช่วยรักษา state แต่ไม่ขยายเป็นการตรวจทุกเมนู/ทุก tender/ภาษีทุกแบบ

ให้ embedded showcase เริ่มฉากเองเมื่อเห็น iframe ส่วนหน้า full-window จะยังเปิดให้ลองได้ถ้ามีอยู่แล้ว ใช้โหมดแสดงผลงานแยกชัด ไม่ปิด interaction ทั่วหน้า standalone โดยไม่จำเป็น

จุดภาพที่ต้องตรวจ: wrapper มี min-width 700 px ทำให้บนมือถือเลื่อนแนวนอน ต้องจัดมุมมองที่ยังเห็นเหตุการณ์กับ ticket ได้ หรือมีภาพรวมกับดูใหญ่ โดยไม่เปลี่ยน product layout ภายในเพื่อยัดลงจอเล็ก Loading terminal ต้องไม่ค้างซ้อนบนภาพโหลดเสร็จ

ตรวจรับ: ไม่กดก็เห็นเพิ่ม→แก้→อัปเดต; preview กับยอดที่ยืนยันไม่ขัดกันในภาพสุดท้าย; ไม่มีสถานะ “receipt printed” ในช่วงที่ยังไม่จบฉาก; แสดงครบโดยไม่ต้องเลื่อน iframe เอง

### 5.7 Claims — ให้ความต่างก่อน/หลังเห็นเอง

ไฟล์หลัก: `ClaimsSkeleton.tsx`

ลำดับ: earlier flow สั้น ๆ ให้เห็น context หาย → transition ระบุว่าเป็น revised flow → skeleton ยังอยู่ขณะเลือก policy → เหตุผลของ policy ที่ใช้ไม่ได้แสดงชัด → ผล conversion พร้อม policy ที่เลือก

ไม่ใช้ความผิดพลาดใน earlier flow เป็น defect ที่ต้องลบ เพราะเป็นเนื้อหาของการเปรียบเทียบ แต่ต้องทำให้ผู้ชมรู้ว่ากำลังดู “ก่อน” และ “หลัง” เสมอ

เก็บการแก้ pending count/success ปรับเหตุผลของ policy ไม่ให้ต้อง hover หรือกดจึงอ่านได้ในช่วงสาธิต เอา modal ที่ซ่อนด้วย opacity แต่ยังรับ Tab ออกจาก accessibility tree เมื่อปิด ถ้าจำเป็นต้องมี delay ก่อนจบให้ยกเลิกได้เมื่อ reset/เปลี่ยนฉาก

ตรวจรับ: เห็นข้อด้อยของก่อนและสิ่งที่แก้ในหลังโดยไม่คลิก; success ไม่เหลือ 1 awaiting; ไม่แสดง success ซ้อนกับ chooser ที่ยังดูพร้อมยืนยัน; Replay คืนฉากเริ่มต้นครบ

## 7. วิธีลงมือและส่งตรวจ

### รอบ A — baseline และ scene specification

1. บันทึกภาพต้น/กลาง/จบของแต่ละ showcase จาก build ปัจจุบันก่อนแก้
2. จด defect ด้านภาพและเรื่องเล่าจากภาพจริง ไม่เหมารวมปุ่มไม่ทำงานเป็นบั๊ก
3. กำหนด fixture, scene order, dwell time, terminal frame และ reduced-motion frame รายโปรเจกต์
4. แยก diff ที่เก็บ/ปรับ/ถอนตามตารางด้านบนก่อนแตะ component

### รอบ B — แก้เส้นทางการดู

ทำทีละโปรเจกต์ตามลำดับ Vitae → Stellareat → Profita → Invitrace → Allianz → Claims → Tims เหตุผลคือสามงานแรกถูกเปลี่ยนทิศทางเป็น click-first ไปแล้ว ต้องคืนวิธีเล่าให้ถูกก่อน

ถ้าต้องใช้ abstraction ร่วม ให้เริ่มจาก hook ขนาดเล็กที่จัดเวลา visibility pause/replay และ cleanup ไม่สร้าง framework ใหม่ ไม่ให้ controller ไป query แล้ว click DOM แทนผู้ใช้ ใช้ state transition ที่ component รับรู้โดยตรง

### รอบ C — visual QA

ตรวจ default desktop และ viewport 1440, 1024, 768, 390, 320 px ที่ zoom ปกติ บันทึกข้อจำกัดที่ยังเหลือแยกจากผลผ่าน

ตรวจทุกหน้า 3 ช่วง: first frame, ช่วงเปลี่ยนฉาก, terminal frame แล้วเลื่อนออก/กลับและกด Pause/Replay อย่างละรอบ ตรวจ tab ซ่อนแล้วกลับ ไม่ต้องทดสอบแอปเหมือนระบบ production

สำหรับข้อความเล็ก ให้ดู screenshot ที่ขนาดใช้งานจริง บันทึก element ที่อ่านไม่ออกจริง แก้ขนาดกรอบ/พื้นที่แสดงหรือจำนวนภาพต่อแถวอย่างพอดี ไม่ลด font ลงอีกทั้งระบบเพื่อให้พอดี

### รอบ D — ตรวจโค้ดและส่งงาน

- type-check, build และ diff check ต้องผ่าน
- focused tests เฉพาะลำดับ scene, pause/cleanup/reset และ fixture ที่คำนวณ ไม่เขียน test ทุกปุ่มจำลอง
- server preview เสิร์ฟ `out/` จึงต้อง rebuild ก่อนตรวจ หลีกเลี่ยง dev/build เขียน `.next` พร้อมกัน
- สรุปรายโปรเจกต์ว่าพบอะไร แก้อะไร พร้อมภาพก่อน/หลังที่เห็นความต่าง ห้ามใช้ “กดได้ครบ” เป็นหลักฐานว่างาน showcase ดีแล้ว
- จบเมื่อผู้ชมดูโดยไม่คลิกแล้วเห็นประเด็นครบทุก case, ฉากสุดท้ายสะอาด, ไม่มี state ขัดกัน, และพื้นที่แสดงผลไม่พังในขนาดที่ทดสอบ
- ไม่ push/deploy จนกว่าจะมีคำสั่งให้เผยแพร่รอบใหม่

## 8. สิ่งที่ไม่อยู่ในงานนี้

ไม่เพิ่ม backend, AI จริง, payment จริง, medical scoring จริง, ระบบ onboarding หรือ error flow ทุกกรณี ไม่เปลี่ยน hero/copy ทั้งหน้าอีกรอบ ไม่ย้ายเดโมข้าม section โดยไม่มีปัญหาภาพที่ตรวจพบ และไม่กล่าวอ้างผลลัพธ์ธุรกิจใหม่เพื่ออธิบาย animation
